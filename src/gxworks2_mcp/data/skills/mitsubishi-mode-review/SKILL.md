# 三菱模式与报警审查

依据用户要求审查行为，优先核对已有程序及接线。不要给所有设备规定同一种停机、夹持或复位方式。

## 建立工艺判据

按本题实际存在的模式列出：进入条件、允许运动、保持量、退出条件、恢复方式，以及同时出现输入时的优先级。需求已明确就沿用；缺项先标假设，只有会改变动作或接线的关键缺项才追问。

重点核对：

- 启动是沿触发还是电平；停止优先级；一直按住启动是否会在故障解除后重启。
- 暂停、正常停止、有序停机、急停是否按需求区分。明确哪些输出和计时保持，哪些复位；阀型和负载可能改变合理选择。
- 报警的置位、保持、解除条件、复位许可是否完整。复位后是否仅恢复待机，或按用户明确要求继续运行；不能隐式把复位接成启动。
- 手动/自动是否同时争用输出，模式切换时是否会跳步或遗留保持位。

## 使用实际证据

1. 存储程序用 `gx_where_used(name, device)` 查写入和读取，`gx_trace_device(name, device)` 查驱动条件；原生 SFC 用 `gx_sfc_read(path)` 保留步骤与动作上下文。
2. 使用 `gx_program_validate`、`gx_lint_program` 定位结构和写入语义。SET/RST 配对、不同 STL 步复用输出不自动等于错误；也不能据此认定并发路径安全。
3. 比较、运算及保持状态涉及数据或历史时，分别说明已确认的条件和还缺的证据。不能只看最终 Y 输出来解释此前的行为。
4. 每条发现写出触发条件、回路/步骤依据、实际后果及针对性修复；再列出能区分修复前后的测试。

三菱要点：M8040 只禁止步骤转移，步内程序仍执行；它本身不能保证输出关闭或计时冻结。相邻 STL 步复用同一定时器可能保留当前值。具体语义按匹配 CPU 手册核对。

## 修改与验证

用户授权修复时，沿用已有版本化补丁、另存及原生检查流程。仅为实际改变的行为补用例，保留必要整工程检查；未改动且哈希一致的编译结果可以复用。

至少为发现的风险选择对应场景：同时启停、故障中启动、故障未消失时复位、切换模式、暂停后松开按钮、恢复后的输出及步骤。不要无条件扩充无关模式或模板。

PLC 应用逻辑和软件仿真不替代设备独立保护。审查报告不能称为实体安全验收。
